## 2. 實測結果（修正盤點時的推測）

**環境**：桌機 Chrome、RTX 4070 Ti、模擬 390×844、DPR 2；這不代表手機。

**牧場 3D**：QA 存檔有 5 隻夥伴，加上食物與排泄物共 13–14 個角色。

- 兩張全螢幕 canvas，各為 780×1688。
- Three.js：draw calls 36–50，三角形 104,344，貼圖 21。

| 每個 ticker 週期 | 中位 | p95 |
|---|---|---|
| 整體 | 8.8 ms | 11.3 ms |
| 原生育成模擬（每週期推進 2 個原生幀） | **5.5 ms** | 7.9 ms |
| 牧場呈現更新 | 3.0 ms | 3.9 ms |
| └ 其中 Three 同步加繪製 | 0.9 ms | 1.3 ms |
| └ 其中診斷值寫入 DOM | ≈0 ms | 0.1 ms |

**結論**：
- 盤點時懷疑的「每幀診斷值寫 DOM」「陰影貼圖每幀重畫」在桌機上加起來不到 1 ms，**不是瓶頸**。
- 最大成本是原生育成模擬：5 隻夥伴時約每原生幀 2.7 ms，16 隻時可能更高。
- 換算到中階手機（CPU 常慢 3–5 倍），每週期可能超過 30 ms。必須到實機確認；若屬實，下一步是對模擬做取樣剖析，且不可改變原作行為。
- 量測方法：暫時加入計時點，量完已全部還原。

**存檔大小**：QA 存檔 15,211 bytes（上限 65,536 的 23%）。每隻夥伴約 1.3 KB；16 隻滿員估計 31–35 KB（約 50%）。換日、進化後實測長到 18 KB。目前沒有立即風險，但新增背包、世界配置等資料前要先估算容量。

## 5. 提案 C：Arena 雙人

**現有基礎**：確定性模擬（種子、固定 1/60 步長、`step(input)`）。缺少：第二份輸入、快照與還原、整數步數計時。

1. **同機雙人（先做）**：把輸入來源抽象化，AI、鍵盤 A／B、Gamepad、觸控都是同一種輸入來源，讓對手位置可以接真人。桌機用鍵盤分區或兩支手把；手機與平板建議**橫向左右分控**（直向優先的例外，需 Owner 同意）。
2. **跨裝置連線（後做）**：
   - 輸入同步加回滾。
   - 傳輸先用 WebSocket 中繼與房間碼，可與帳號後端共用。
   - WebRTC P2P 留作日後的延遲優化（仍需 signaling，約一成連線需要 TURN）。
   - 前置工作：`snapshot()`／`restore()`；招式時序改為整數步數；確定性稽核（`Math.atan2`、`hypot`、`sin`、`cos` 在 V8 與 JavaScriptCore 之間不保證位元一致），配合狀態雜湊比對與主機快照重同步；輸入延遲 2–3 幀、回滾上限約 8 幀。
3. 同機完成**不代表**連線完成，兩者分開驗收。
