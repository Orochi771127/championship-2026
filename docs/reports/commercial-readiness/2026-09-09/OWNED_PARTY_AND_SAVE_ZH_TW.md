# 第一階段進展：自有隊伍與存檔穩定性

基準 main `74b264f44f94bc74a48c4f73b2d20e349533cfa3`。這是第一階段中的已完成工程範圍；整個第一階段仍為 PARTIAL。

## 已接入正式流程

- 頭銜賽先選擇玩家持有的個體，按比賽條件、成長階段、身體狀況及名額限制參賽。取消選隊不扣款；確認時重新檢查資格及金額。
- 帶入該個體當前 HP、TP、訓練數值與已學招式，保留 instance ID。原作個體結果 writer 回寫出戰次數、勝場、HP／TP、壓力等欄位；個體、頭銜進度與錢包仍由現有 application 交易提交，重复結果不重複入帳。
- 戰鬥使用既有 217-channel gameplay RNG。準備階段只操作候選副本；成功扣款時一起接入 application，後續戰鬥與存檔共用同一物件。被拒絕的候選不消耗玩家亂數。
- 選隊時收起賽事立方體與模式說明，390px 畫面可顯示個體及確認／返回操作。DOM 處理介面，沿用同一 Pixi stage；沒有新 router、store、save 或 ticker。
- 支援 Web Locks 的瀏覽器在開啟遊戲前取得獨占存檔鎖，儲存並離開後釋放。另一分頁收到明確繁中提示，可在原分頁離開後重試。未支援 Web Locks 的環境仍有 stale-byte 拒寫檢查，但不宣稱同時競爭下的原子互斥。
- 儲存失敗保留當次可序列化進度；育成畫面提供 JSON 匯出。查詢存檔、檢查 Continue 及重試不會偷偷採納其他分頁的版本。尚未建立完整匯入復原操作，因此整個「存檔復原」項目仍未關閉。

## 原作證據

`scripts/research/check-battle-party-cpu.py` 對既有 SHA-256 固定的原作執行：

- ARM9 `02092380 / 02092244`：34 個頭銜條件索引 × 228 物種 × 3 組個體條件，共 **23,256 組**。CPU 比較指出資格 loader 的一個欄位實際來自 catalog `field24`，已按該讀址接入。
- OVL19 `0210E5AC..0210E798`：mode 0／1、type 0 的受控個體結算，共 **216 組**。只覆蓋此 writer 的輸入輸出，不代表外圍大會與 UI 已驗收。
- OVL19 `02113E04..02113E48`：物種招式後追加個體 `12c / 130` 已學招式，保留次序及重複值。

完整 CPU receipt 在 `docs/research/BATTLE_PARTY_QUALIFICATION_CPU_2026-09-09.json`。產品只讀取功能性條件資料；原始 ROM、CPU executable 及 RAM snapshot 不進入 runtime。

## 驗收與界線

完整本機回歸 **1,397 pass / 0 fail / 0 skip**，101.71 秒。測試包含全部資格／writer CPU 向量、實際戰鬥模擬、一次性結算、戰後新建 application 的 Continue、共用 RNG、選隊取消／名額限制、分頁互斥與儲存失敗匯出。

瀏覽器使用獨立 `127.0.0.1:8766`，以 `tests/fixtures/championship-owned-party.html` 準備明確標示的成年個體／日期存檔，再從正式 LOGIN／Continue、系統→對戰、選隊、確認進入實際戰鬥。已直接檢視選隊與戰鬥畫面，觀察雙方攻擊、扣血及落敗結果，走完獎金 0、返回育成、儲存與重新載入。結果翻頁另以鍵盤確認，不能把此步驟算成實體手機觸控驗收。第二分頁被拒、原分頁儲存離開、第二分頁重試成功亦已實際操作。

此測試以受控成年存檔起跑，**不是**正常新遊戲養成到成年／狩獵／完整多輪大會驗收。完整互動教學、所有晨間來源／形態配對、特殊 Hunt 堆疊方向、全角色戰鬥策略與所有動作視覺驗收仍開放。已追到大會的 3／5 輪結構及各輪對手表，但尚未把 helper 或讀表結果稱為可玩多輪大會。

本次依 `game-studio`、`web-game-foundations`、`game-playtest`、`game-ui-frontend` 技能執行既有架構整合、正常入口試玩及手機尺寸畫面檢查；原作證據與 Owner Direction 仍優先。權利核驗依要求保留在最終發行前，本次不公開部署。
